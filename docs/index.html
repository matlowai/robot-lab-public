9

A patrol robot, evaluated first

Spot walks a compound on NVIDIA's pretrained legs while staged incidents happen around it. The scorer existed before the robot did.

Lesson 9.1

Build the scorer before the thing it scores

Milestone M0 had no simulator at all: event rules (perimeter crossing, restricted zone, a fall, a vehicle in the wrong place, a gate left open, an obstacle on the route), a scorer, and scenario files that stage those incidents at known times. Only then did Isaac Sim join, in M1: Spot on NVIDIA's pretrained walking policy, walking a generated compound, with the rules reading facts back from the simulated stage.

  • Ground truth comes from what the scenario staged, never from what the rules detected. Scoring rules against their own output always gives 100%, so the scorer refuses rule output as truth, and a test checks that.
  • Test that the tester can fail. Drop a staged incident, add a phantom one, shift the times: the scorer must report each.
  • The M1 gate: both base scenarios pass in Isaac (all six incident types, 0 false alerts, full coverage), then 10 of 10 randomised variants, with every actor's timing shifted and its staged truth shifted with it.

Before any simulator: write event rules over a per-frame fact stream (tracks, zones, asset states), a scorer that matches detected incidents to incidents staged in a scenario file within a tolerance, and mutation tests that prove the scorer fails when an incident is dropped, invented or shifted. Then drive the same rules from Isaac Sim by rebuilding each 10 Hz frame from the stage itself (prim poses, gate hinge angles), never from the scenario file.
10

Avoiding people it can't predict

A simulated lidar, a hand-written local planner, and book readers who walk straight at the robot.

Lesson 10.1

An avoidance result means nothing without a control

Spot got a PhysX ray-cast lidar and a dynamic-window planner: sense, track, predict, choose a velocity. Against six oblivious book readers it finished the patrol with no near misses. The number only counts because the control run, the same patrol with avoidance switched off, walked into three of them and was knocked over.

Every planner bug showed up first in a 2-D world with circles for people, which runs a whole patrol in seconds:

  • Stalling short of the goal: scoring progress at the end of a rollout punishes the final hop. Score the closest approach.
  • Getting run over: treating each scan as frozen makes a head-on walker look static. Track velocities across scans.
  • Flip-flopping left and right: equal scores flip every tick. Commit to a side for a few seconds.
  • Phantom motion on walls: grazing-angle lidar hits slide along a wall as you move. Trust velocities only from clusters.

What we learned

  • Learned legs plus hand-written avoidance is a legitimate hybrid. Know which part is which before saying "it did it on its own".
  • Debug the planner in the cheap world; spend Isaac time only on what the cheap world can't show, like falls.
11

The night the editor died

An overnight bake-off that lasted two minutes and took the editor with it.

Lesson 11.1

Long jobs get their own cgroup

The overnight plan said "keep 20 GB free". The launcher checked free memory, then started six Isaac processes in the same second, and a seventh smoke test was already running. Every check saw the same free memory. All of them were children of the coding session inside VS Code, so when memory pressure hit, systemd-oomd killed the whole VS Code scope: 59.5 GB, the editor, the session, the orchestrator and every run.

  • nohup doesn't help. The out-of-memory daemon acts on the whole scope, not the process.
  • The relaunch ran each job as its own memory-capped unit and started Isaac processes one at a time, 90 s apart, only with 29 GB free. It ran all day with RAM never below 20 GB free.
Reproduce with a coding agentpattern
systemd-run --user --unit=patrol-night --collect -p MemoryHigh=44G -p MemoryMax=50G \
  --working-directory=$PWD uv run python tools/overnight_patrol.py --stages s1,s2 --parallel 4
journalctl --user --since "-1h" | grep -i oom        # what oomd did, if anything

The bake-off gets honest

Hand-written planner against a reinforcement-learning policy, on the same crowds. The first answer was confounded, and a video showed it.

Lesson 12.1

Watch the video, not just the table

The RL policy looked "stuck" at the end of a three-way comparison video. It was parked: it had finished the patrol 40 seconds early. The book readers were keyframed to a timetable fitted to the no-avoidance robot, which stops and turns in place. The planner and RL turn while walking, ran 10–13% ahead, and outran their encounters. The "collisions" at the end were late readers walking into a robot that had already gone home.

Lesson 12.2

Opponents that react to the thing under test

The fix was a closed-loop crowd of about 50 people: wanderers reading books, loiterers standing on the route, and hunters posted beside every patrol leg. A hunter sees Spot (range, vision cone, line of sight that buildings block), locks on, predicts where it's going and walks to intercept. Inside 2.5–4.5 m it commits to a straight line and stops re-aiming. A pursuer that re-aims until contact at walking speed can't be escaped, and then there's nothing to learn.

Both contenders now get the same exposure. The cheap world was then checked against Isaac on the same 8 seeds: 6.1% hits per commit in Isaac, 7.9% in 2-D. Isaac adds what 2-D can't express: 3 of the planner's 7 hits knocked Spot over.

Write one closed-loop crowd model used by every consumer (2-D benchmark, Isaac runner, torch RL env): wanderers, loiterers and hunters posted beside each patrol leg. Hunters lock on when the robot is in range, inside a vision cone and not hidden by buildings; they aim at a constant-velocity intercept, re-aim every 0.5 s, and commit to a straight line inside commit_m. Lesson 12.3

Report the denominator

Hit-per-commit is conditional. A contender that's slower meets more hunters; one that falls early meets fewer; one that bumps ordinary people doesn't show up in it at all. On 80 held-out hard-tier seeds:

Planner38.5%24.027/80377 s
RL, 2 lidar frames 0.1 s apart37.2%28.361/80462 s

Longer lidar memory helped against hunters and made RL much faster, but RL still bumps ordinary people twice as often. Its training world had 4–8 people per scene; the benchmark has about 50.

Lesson 12.4

Privileged information leaks through the scene

Hunters had debug beacons that turned magenta when locked on. Spot's head camera, which records the training data for a vision policy, could see those beacons from about 4 m. The data would have told the model each hunter's hidden intent. Debug visuals are now invisible whenever the head camera records, and a check counts forbidden pixels: 0 in 600 frames that included 5 lock-ons.

What we learned

  • Scripted opponents must react to the thing under test, or a faster contender just outruns them.
  • Check a cheap simulator against the real one on the same seeds before trusting it.
  • Keep debug-only visuals on a layer the learner's sensors can't see, and test it by counting pixels.
15

Teaching it to yield

The learned policy dodged hunters but kept bumping ordinary walkers about twice as often as the hand-written planner. Six fixes failed. What worked was asking what the robot could actually perceive, then giving bystanders their own price. 2026-09-26 → 10-03.

Lesson 15.1

One change per arm, and a script that killed three runs

Contact forensics had shown that RL bumps people it had seen for about 3 seconds while it kept walking at full speed. Its forward-speed action had collapsed into a go/stop switch. So the next night ran four pre-registered arms, one change each. Checkpoints were picked on validation seeds, each pick ran once on 80 sealed seeds, and the win rule was written down before launch.

80 sealed seedsRuns bumping ordinary peopleHunter hitsMedian patrol
Planner (the bar)27/8038.5%377 s
Baseline51/8031.0%382 s
Speed channel fixed49/8028.4%368 s
+ time-to-collision penalty55/8031.0%377 s
+ warm start from a clone of the planner55/8023.2%352 s

The speed fix worked as a mechanism: the action came back to life, with 15% of steps at in-between speeds. But contacts didn't fall, so speed wasn't the bottleneck. Three of the arms almost didn't report at all. While they were running, I edited the shared launch script for the fourth. Bash reads a script lazily, so seven hours later they resumed at a shifted offset and died with unexpected EOF. A parse error skips the error trap, so their status said "running" forever.

What we learned

  • Pre-register the arms, the selection rule and the win rule before the run, so a "no" is still a clean answer.
  • A diagnostic passing (the speed channel is alive) is not the behaviour improving. Check both.
  • Never edit a script a running job is executing. Launch every long job from a frozen copy.

Lesson 15.2

Can a network even copy the planner?

Six 7-hour fixes had all changed the reward or the behaviour. None asked whether the policy's input contained the cue. The policy saw three lidar snapshots 0.3 s apart, and in that time a crossing walker moves less than one lidar sector. The cheap test is imitation: clone the planner from the candidate input, change nothing else, and see whether the copy yields. If imitation can't recover a behaviour from an input, RL almost certainly can't either.

Lesson 15.3

Give it velocities, and check the emulation

The GPU training world can't run the real tracker, so it emulates it from the true positions. People must be hit by at least two rays, velocities are smoothed and only trusted from the third scan, and 0.2 m/s of noise is added. Before training, the real tracker was run on the training world's own scans and compared direction by direction: 98.5% agreement on what is moving, direction cosine 0.996. At deployment and in every score, the real tracker supplies the velocities.

Every arm improved, on every measure. It still wasn't the planner. The literature said the same: in DRL-VO, a policy with pedestrian velocity inputs but only distance penalties stayed below a hand-written planner until a predicted-conflict reward was added.

What we learned

  • Ask "can it perceive this?" before "how do I reward this?".
  • Information makes the right behaviour learnable. It doesn't make it worth learning.
  • When training emulates a sensor, measure the emulation against the real sensor on the same data, and evaluate through the real one.

Lesson 15.4

A separate price for bumping bystanders

One −10 contact penalty covered hunters and bystanders alike, and 7 of 8 training contacts were hunters. The best move against a hunter (keep speed, sidestep) is exactly wrong for someone crossing your path (slow down, let them go). So the reward stayed the same, and a separate cost was added for ordinary people only. It charges for driving into where each walker will be in the next few seconds, for closing speed when near, and for contact. Constrained RL (PPO-Lagrangian) gives the cost its own critic, and a multiplier that rises automatically until the cost is under budget. Nobody hand-tunes the weight.

How far ahead should it look? The question came from driving: you track cars 20 s out, and things that loom grab your attention. A 12 m lidar at walking speeds gives about 4–6 s of warning, so we tested 2 s against 5 s, with two training seeds each.

In plain words: once it could see where people were heading and had a separate price for crowding bystanders, the learned robot bumped people about as often as the hand-written one. It dodged the people chasing it 2.5× better and finished patrols about 10% faster.

Two of four runs beat the planner on every criterion. The pre-registered demo pick (the best validation score, 5 s seed 0) did not, and naming a winner after seeing the test would be cherry-picking. 2 s versus 5 s couldn't be separated: the random seed moved results by 6–10 runs, as much as the look-ahead did.

What we learned

  • One shared penalty for different failures lets the common one set the price. Price each failure separately, and let a budget set the weight.
  • Penalise what's coming (predicted conflicts, closing speed), and only penalise what the learner can observe. The same time-to-collision idea failed before the policy could see velocities.
  • Look-ahead is a design parameter, set by sensor range ÷ closing speed. Looming (time to contact per direction) as an explicit input is the next experiment.
  • Replicate on a second training seed before comparing two variants.

Lesson 15.5

The winner's curse

Every RL run looked better on the 40 validation patrols than on the 80 sealed ones, and I first wrote that the sealed seeds were "harder for RL". They weren't. Each run kept the lowest of 14–18 checkpoint scores, and each score was a noisy estimate from 40 patrols. The minimum of many noisy numbers is mostly the luckiest one.

Runs bumping ordinary peopleValidation, picked checkpointValidation, all checkpointsSealed test
Lidar only (4 runs)42–55%56–73%61–69%
+ velocities (3 runs)28–32%47–51%45–52%
+ bystander cost (4 runs)18–25%31–32%25–38%

Averaged over checkpoints, validation matches the test. It even ranked the last runs backwards: the best-validation run tied worst on the sealed seeds. My first explanation leaned on one anecdote ("that pick was the last checkpoint, so it isn't selection"), and the statistic overturned it. The next protocol picks on far more patrols, or fixes the checkpoint in advance.

What we learned

  • Picking the best of many noisy scores flatters the pick. Use a much larger selection set, or a rule with no picking, and look at the average as well as the best.
  • Settle a suspicion with the statistic, not an example.
  • Ask whether a gap is distinguishable before calling it a win: 20 vs 27 of 80 is p ≈ 0.3. Pool replicates for the claim.

Lesson 15.6

Before you train a robot to share space with people

These are the questions that would have saved the most time, in order:

  1. Can the policy perceive the cue? List what a good human or a hand-written controller uses (here: which way each person is moving), and check it's in the input at the rate the decision needs. Test it by imitation before any RL.
  2. Does the reward price each failure separately? Chasers and bystanders need opposite responses. A shared penalty is set by whichever is more common.
  3. Does the signal arrive early enough to act on? Contact is too late. Predicted conflicts and closing speed arrive seconds earlier, while braking still helps.
  4. Does training contain the situation, as often as the robot meets it? Count what's near the learner, by kind, per step, not headcount per scene.
  5. Can the policy actually act? Watch the action distribution. A saturated output can turn "speed" into an on/off switch.
  6. Is the evaluation honest? Opponents that react to the contender, exposure reported beside rates, a control run, sealed seeds run once, enough data to pick checkpoints, more than one training seed, and the reading rule committed before you look.
  7. Will the pipeline tell you when it fails? Frozen launch copies, resumable stages, deadlines with fallbacks, memory caps, and no status that can say "running" forever.

Gotchas

Quaternions are xyzwIsaac Lab 3.0 uses x, y, z, w. A 90° yaw is (0, 0, 0.707, 0.707).
ProxyArray, not tensorsSim data fields are Warp-backed. Call .torch before TorchScript math like quat_apply.
Instanced assets ignore overridesMass settings silently don't apply. Use startup events (friction via randomize_rigid_body_material).
Stale first frameThe first render after a reset is old. Drop the first frames of every episode.
libxml2 on Ubuntu 26.04Only libxml2.so.16 exists, which breaks FBX/OBJ import. URDF/MJCF importers bundle their own converters.
Don't kill yourselfpkill -f pattern can match the shell running it. Anchor the pattern to the interpreter path.
Soft gripper defaultThe SO-101 IK task caps grip torque at 1 N·m for cubes. We use 3 N·m.
Success detectors lieOurs counted a bowl flung through the table as a success. Watch every "success" episode before reporting a number.
One seed, one bad layoutA fixed eval seed replays the same broken reset for every policy. Seed per episode.
Match the start stateDemos began with the jaw at 16; eval began at 9. The policy kept the jaw shut for 20 s.
Chained background jobsWaiting on log markers spawned duplicate runs twice. Wait on process IDs instead.
nohup won't save yousystemd-oomd kills a whole scope. Run long jobs as their own systemd-run --user -p MemoryMax=… units.
Free-RAM checks raceSix launches that check free memory in the same second all see the same number. Launch one at a time, after the last one has grown.
Never edit a running scriptBash reads scripts lazily. An edit made while a job runs it can kill the job hours later with a parse error that skips the ERR trap. Launch from a frozen copy.
The best checkpoint is the luckiestThe minimum of 14 noisy 40-episode scores looked 10–20 points better than the test. Select on far more episodes, or not at all.
Scene-data arrays go staleIsaac Lab reallocates transform buffers on hard reset. Re-read every frame; never cache the array.
